# Backup Full / Incremental — 2026-10-13

## ขอบเขตและผลลัพธ์

เตรียมระบบ Backup v3 สำหรับ Firestore `(default)` ของ `PROJECT_ID` ที่ระบบ SYY-Shop ใช้อยู่ ครอบคลุม Collection หลักและ Subcollection ที่ค้นพบจริง รวม Collection ที่เพิ่มใหม่และข้อมูลย่อยใต้ parent document ที่ถูกลบไปแล้ว ไม่เปลี่ยน schema, indexes, IAM, สิทธิ์บัญชี หรือข้อมูล Production

ปลายทางตามที่ผู้ใช้ระบุ: [โฟลเดอร์ Backup ใน Google Drive](https://drive.google.com/drive/folders/1QqJRj1vet9nkcAn8-bfKDStnhXKGQqWk)

- Full ทุกวันอาทิตย์ประมาณ 22:00 เวลา `Asia/Bangkok` เก็บ 4 รุ่นล่าสุด
- Incremental ทุกวันประมาณ 22:00 รวมวันอาทิตย์ บันทึกเอกสารที่เพิ่ม/แก้ไขและ path ที่ถูกลบ
- วันอาทิตย์ใช้ snapshot ของ Full ร่วมกัน จึงสร้าง Incremental ว่างที่อ้างอิง Full ใหม่ได้โดยไม่อ่าน DB รอบที่สอง
- หากยังไม่มี Full จะสร้าง Full เริ่มต้นและ Incremental ก่อน ครั้งต่อไปจึงเก็บเฉพาะ delta
- Full ที่กดสำรองเองนับรวมใน 4 รุ่น เมื่อหมดอายุ Full จะย้าย Incremental ที่พึ่งพารุ่นนั้นไป Trash ด้วย
- ไม่คัดลอกหรืออ่าน binary ของรูป แต่สำรอง `Product_Images` และ URL / File ID / metadata ใน DB ตามเดิม การกู้คืนจึงยังอาศัยรูปต้นฉบับ
- รองรับการตรวจและกู้คืน Backup v2 เดิม ไม่ลบหรือย้ายไฟล์รุ่นเดิมและรายการ Drive ที่อยู่นอกโครงสร้าง v3

โครงสร้างปลายทาง:

```text
โฟลเดอร์ที่ผู้ใช้กำหนด/
  <PROJECT_ID>/
    Full/
      YYYY-MM-DD/
        full_HH-mm-ss_<UUID>/
          manifest.json
          index.json
          script-properties.json
          <Collection>/part-N.json
          <Subcollection>__<path-hash>/part-N.json
    Incremental/
      <Full-folder-ID>/
        YYYY-MM-DD/
          incremental_HH-mm-ss_<UUID>/
            manifest.json
            index.json
            script-properties.json
            <Collection ที่เปลี่ยน>/part-N.json
```

`manifest.json` ระบุ Collection path เดิมทั้งหมดและผูกไฟล์กับ project, โฟลเดอร์, วันที่, snapshot time และ Full ต้นทาง ข้อมูลสำรองเก็บ raw Firestore typed fields เพื่อไม่ทำ integer, bytes, references, map, array, null, timestamp หรือ geopoint สูญหาย

## ปัญหาเดิมและการป้องกัน

ระบบเดิมใช้รายการ Collection คงที่ สำรองรวมไฟล์เดียวและคัดลอกรูป ตั้งเวลาอาทิตย์ 02:00 และเก็บ 8 รุ่น จึงไม่ตรงกับความต้องการใหม่ และไม่ครอบคลุม Collection / Subcollection ใหม่โดยอัตโนมัติ

การแก้ไขหลักอยู่ใน `Code.gs`:

- ใช้ `listCollectionIds` ทั้ง root และทุก document / missing parent พร้อม pagination และ `showMissing=true`
- อ่านเฉพาะ Collection ที่พบจริง ไม่ยิง document-list เพิ่มตามรายชื่อ Collection คงที่ที่ไม่มีอยู่ใน DB
- ทุกคำขออ่านข้อมูลใช้ server `readTime` เดียวกันจาก query ขนาด 1 document เพื่อรักษา snapshot ขณะระบบขาย/แก้สินค้าใช้งานอยู่
- ใช้ SHA-256 ตรวจ manifest, index, properties และ part files ตรวจ Full + Incremental chain ก่อนสร้าง delta หรือกู้คืน ไม่ต่อ chain จากไฟล์ที่เสียหายหรือหายไป
- ใช้ UserLock ของเจ้าของ Backup โดยไม่ยึด ScriptLock ที่ธุรกรรมขายใช้
- ไม่เผยแพร่ manifest ของชุดที่อ่านไม่ครบ และไม่เลื่อน state เมื่ออ่านหรือเขียนล้มเหลว โฟลเดอร์ที่ยังไม่สมบูรณ์ถูกย้ายไป Trash แบบกู้คืนได้
- ตรวจโฟลเดอร์และ ancestor ว่าเป็นของเจ้าของสคริปต์และไม่แชร์ เพราะ Backup มีบัญชีและคีย์กู้คืน TOTP ไม่เปลี่ยน sharing ให้เอง หากปลายทางแชร์อยู่จะหยุดก่อนอ่าน DB
- ไม่เผยแพร่ Backup ของผู้ใช้ที่เปิด TOTP หากไม่มี `AUTH_MASTER_KEY`; หยุดหาก durable Script Properties เปลี่ยนระหว่าง capture
- จำกัด 4 Full ที่ผ่านการตรวจจริง ไฟล์เสียหายไม่นับเป็นรุ่นกู้คืนที่ใช้ได้ หาก retention ล้มเหลวจะรักษา Full ที่สำเร็จและแสดง warning
- ย้ายปลายทางแล้วเริ่ม chain ใหม่ในโฟลเดอร์ใหม่ ไม่ใช้ baseline เก่าข้ามปลายทาง และไม่ข้าม Backup เพราะ marker ของโฟลเดอร์เก่าในวันเดียวกัน
- ทริกเกอร์ใหม่ถูกสร้างก่อนลบทริกเกอร์ Backup เดิม การขอสิทธิ์/quota ล้มเหลวจะไม่ลบทริกเกอร์เดิม ทริกเกอร์งานอื่นยังอยู่
- Backup ตามตารางที่สำเร็จแล้วในวันเดียวกัน/ปลายทางเดียวกันจะไม่อ่าน DB ซ้ำ

หน้า Backup เพิ่มสถานะตารางเวลาจริง แสดง Full / Incremental และจำนวนเปลี่ยน/ลบ มีปุ่มตั้งตารางเฉพาะ admin เปิดหน้าต่างอย่างเดียวไม่สร้าง Trigger หรืออ่าน Firestore ผ่าน Backup

## Firestore Read / Write Impact

**Incremental นี้ลดขนาดไฟล์ ไม่ลดจำนวนเอกสารที่ต้องอ่านในแต่ละวัน** การตรวจรายการลบให้ครบโดยไม่แก้ DB schema/change journal ต้องเทียบ snapshot ใหม่กับ index ของรุ่นก่อนหน้า

- แต่ละ capture อ่านเอกสารทั้งหมด `N` รายการ รวม Subcollection ที่พบ
- เพิ่ม query ขนาด 1 document เพื่อขอ server snapshot time
- เพิ่ม `listCollectionIds` ที่ root และทุก document / missing parent พร้อม pagination; แต่ละ request มีค่าบริการเท่ากับ 1 document read
- การอ่าน Collection ว่าง/หน้าข้อมูลและค่าอ่านขั้นต่ำของ query ต้องนำไปประเมิน billing ด้วย ไม่ใช้จำนวน HTTP requests เป็นจำนวน document reads ตรง ๆ
- วันอาทิตย์ Full + Incremental ใช้ capture เดียว แทนการ scan สองครั้ง ลดการอ่านซ้ำส่วน capture ของวันอาทิตย์ประมาณ 50% เทียบกับทำสอง snapshot แยกกัน
- ความถี่ใหม่ทุกวันมี Reads มากกว่า Backup สัปดาห์ละครั้งเดิม การค้นหาข้อมูลย่อยให้ครบเพิ่ม discovery reads ด้วย จึงไม่อ้างว่าระบบ Backup ใหม่นี้ลด Reads รวม
- Backup ไม่ส่ง Firestore create/update/delete/commit และไม่อ่าน blob รูป เขียนเฉพาะไฟล์/โฟลเดอร์ Drive และ Backup state ใน Script Properties

แบบจำลอง local: 1,003 documents ใน Collection ใหม่, ขนาดหน้า 10 เพื่อทดสอบ pagination, อ่านเอกสารครบทั้ง Full และ Incremental, document-list requests 101, collection-discovery requests 1,004, snapshot probe 1 ครั้งต่อ capture ขนาด Full ประมาณ 215 KB; Incremental ที่ไม่มีรายการเปลี่ยนประมาณ 79 KB ลดขนาดไฟล์ประมาณ 63% ใน fixture นี้ เป็นค่าทดสอบ ไม่ใช่ผลวัด DB หรือ billing จริง

## การกู้คืนและข้อจำกัด

- Dry run ตรวจ chain และ checksum จาก Drive โดยไม่เขียน DB
- เขียนได้เฉพาะ Staging ที่ว่างและระบุ target/source/confirmation ชัดเจน Source และ target ต้องคนละ project การกู้คืน Production ยังคงถูกปิด
- คง document paths และ typed fields รวมข้อมูลอ้างอิงรูป ไม่สร้างรูปใหม่ เปลี่ยน session version ของบัญชีเพื่อไม่คืน session เดิม
- ใช้ `currentDocument.exists:false`, batch ไม่เกิน 450 writes และ payload ต่ำกว่า 8 MiB หยุดทันทีหาก commit ไม่สำเร็จ การกู้คืนหลาย batch ไม่ใช่ atomic transaction ทั้งชุด ต้องตรวจ Staging หากเกิดข้อผิดพลาด
- จำกัดเวลางานรวมประมาณ 270 วินาทีเพื่อเผื่อก่อน Apps Script execution limit ไม่เผยแพร่ Backup ที่ยังอ่านไม่ครบ ไม่มี resumable worker ในรุ่นนี้ DB ใหญ่มาก/Drive ช้ามากอาจหยุดด้วย error ต้องวัดกับข้อมูลจริงก่อนยืนยันว่า Backup เสร็จภายในเวลา
- ครอบคลุมฐาน `(default)` ของโปรเจกต์ปัจจุบัน ไม่รวม named database อื่น, Firestore rules/index definitions, IAM หรือโปรเจกต์อื่น
- Clock trigger ของ Apps Script ทำงานใกล้ 22:00 โดย `nearMinute(0)` อาจคลาดเคลื่อนประมาณ ±15 นาที ไม่รับประกันตรงวินาที

## สถานะเปิดใช้งานจริง

Source ถูก Commit และ Push ไป `origin/main` แล้วที่ `a119b23b9aca4768ba46f1c86a0a41a7a3c52a9f` แต่ **ยังไม่ได้ซิงก์ Apps Script, ติดตั้ง Trigger หรือ Deploy Web App**

Editor ล่าสุดที่ผู้ใช้ระบุคือ [โปรเจกต์ Apps Script สำหรับเปิดใช้ Backup](https://script.google.com/home/projects/1D8qM4Jga8iKnwQgUjoa0M0jHGWUEyfY6i0IcF7DtKlUJpwTd73AJap1i/edit) ใช้ URL นี้แทน URL เดิมที่ผู้ใช้ส่งก่อนหน้า ยังไม่ยืนยันชื่อโปรเจกต์หรือเนื้อหา Source จาก Editor จริง

ตรวจ URL ใหม่เมื่อ 2026-10-13 แล้วถูกส่งไปหน้า Apps Script สาธารณะ; กด Sign in แล้วพบหน้า Google Accounts ที่ให้กรอก Email or phone ขณะที่โฟลเดอร์ปลายทางยังค้างที่ Sign in เช่นกัน จึงยังตรวจ Source, ยืนยันสิทธิ์ปลายทาง หรือสร้าง Trigger บนโปรเจกต์จริงไม่ได้ ต้องเข้าสู่ระบบใน Browser ของ Codex ด้วยบัญชีที่เข้าถึงโปรเจกต์และโฟลเดอร์นี้ แล้วเปิด Editor ล่าสุดก่อนดำเนินการต่อ

ขั้นตอนเปิดใช้หลังเข้าถึง Editor:

1. เทียบ Source ล่าสุดใน Editor กับ Git เพื่อรักษางานที่ผู้ใช้แก้เอง แล้วอัปเดต runtime 3 ไฟล์ข้างต้น
2. ตรวจว่าโฟลเดอร์ปลายทางเป็นของบัญชีเจ้าของสคริปต์และไม่แชร์ ไม่ปรับสิทธิ์โฟลเดอร์ให้อัตโนมัติ
3. เจ้าของสคริปต์อนุญาต scope จัดการ Trigger หาก Google ขอ แล้ว Run `setupBackupSchedule_` ครั้งเดียวจาก Editor (ชื่อเดิม `setupWeeklyBackupTrigger_` เรียกตั้งค่าใหม่นี้ได้)
4. ตรวจ Trigger `dailyBackupJob_` เหลือหนึ่งตัว ตั้งทุกวัน เวลาไทยใกล้ 22:00 ตัว handler เลือก Full ในวันอาทิตย์และ Incremental ทุกวันเอง
5. ตรวจ Executions และ Drive หลังรอบแรก ยืนยันจำนวนเอกสาร/เวลา/manifest ก่อนรับรอง Production UAT การอัปเดต Web App deployment ต้องดำเนินการตามสิทธิ์อนุมัติของโครงการ

ไม่มี Production data mutation, schema/index/IAM change หรือการเปลี่ยนสิทธิ์ผู้ใช้จากงานนี้
