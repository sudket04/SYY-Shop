## งานค้างตามลำดับ

### P1 — หยุดการลบร่างเมื่อออกจากหน้ากู้ร่าง

**วิธีทำซ้ำ:** เก็บร่างใบเสนอราคา เปิดหน้าซ้ำโดยให้กล่องกู้ร่างใช้ UI สำรองเมื่อ SweetAlert ไม่พร้อม รอให้กล่องแสดง แล้วเปลี่ยนหน้าโดยไม่กดปุ่ม ร่างเดียวถูกลบ หากมีร่างเก่ากับร่างล่าสุด ร่างล่าสุดถูกลบ ส่วนร่างเก่ายังอยู่ ตรวจ `syyDialog`, `swyConfirm` และ `syyDraftStart` ใน [Shared.html](../Shared.html) ปัจจุบัน fallback ส่งผลไม่ยืนยันเมื่อเกิด `pagehide` และผู้เรียกใช้ผลเดียวกันกับการกดปุ่มทิ้งหรือเลือกฉบับก่อนหน้า

**แนวแก้:** ให้คำตอบของกล่องกู้ร่างแยกการยืนยัน การกดปุ่มรอง และการปิดโดยไม่มีคำตอบ ทั้งเส้นทาง SweetAlert และ fallback คงสัญญาแบบ boolean ของ `swyConfirm` สำหรับผู้เรียกทั่วไป หรือเพิ่มทางให้เฉพาะกล่องกู้ร่างอ่านผลเต็ม ลบร่างหรือแทนที่ร่างล่าสุดเมื่อผู้ใช้เลือกอย่างชัดเจนเท่านั้น หากเขียนฉบับที่เลือกลงพื้นที่จัดเก็บไม่สำเร็จ ให้รักษาฉบับที่กู้ได้และแสดงสถานะตามจริง คงการผูกร่างกับบัญชีและสิทธิ์เดิม

**ผ่านเมื่อ:** ทดลองเปลี่ยนหน้าจริงใน Chromium แล้วกลับมายังกู้ได้ทั้งกรณีหนึ่งและสองร่าง ตรวจการกดกู้ กดทิ้ง เลือกฉบับก่อนหน้า เซสชันหมดอายุระหว่างกล่องเปิด และกรณี storage ล้มเหลว ตรวจฟอร์มอื่นที่ใช้ตัวเก็บร่างร่วมกัน จำนวน write RPC และ Firestore Writes เพิ่ม 0

### P2 — รักษาขอบเขตผลค้นหา Dashboard เมื่อประวัติมาถึง

**วิธีทำซ้ำ:** หน่วง `getDashboardBootstrap` ให้สินค้าโหลดก่อน ค้นหาสินค้าคงเหลือ 200 จุดสั่งซื้อ 1 ขณะตารางแสดงสินค้าทั้งหมด เมื่อประวัติมาถึง ค่าเริ่มต้น `DASH.tab='low'` ทำให้สินค้าหายแม้คำค้นและข้อมูลยังเหมือนเดิม ตรวจ `dashRenderCatalogPreview`, `dashLoad` และ `dashRenderHealthTableOnly` ใน [index.html](../index.html)

**แนวแก้:** แยกขอบเขตค้นหาที่ผู้ใช้กำลังใช้จากแท็บเริ่มต้น เมื่อเริ่มค้นหาในรายการสินค้าช่วงโหลด ให้คงขอบเขตสินค้าทั้งหมดตอนประวัติมาถึงจนผู้ใช้เลือกตัวกรองเอง รักษาคำค้นและหน้าที่เห็นหากขอบเขตเดิมยังใช้ได้ ใช้ป้ายบอกขอบเขตให้ตรงกับผลลัพธ์ ข้อมูลสรุปที่ยังโหลดไม่เสร็จต้องแสดงสถานะรอหรือผิดพลาด โดยเฉพาะยอดที่แสดงเป็นศูนย์เพราะยังไม่มีข้อมูล

**ผ่านเมื่อ:** คำค้นเดียวกันยังเจอ SKU เดิมก่อนและหลังประวัติมาถึง เว้นแต่ข้อมูลสินค้าหรือตัวกรองเปลี่ยนจริง ตรวจกรณีประวัติล้มเหลวและลองใหม่ การกดหน้าถัดไปจากข้อมูลในหน่วยความจำ และยอดขาย/ต้นทุน/ผลแก้บิลหลังโหลดครบ การค้นหาและเปลี่ยนหน้าของรายการที่โหลดแล้วต้องเพิ่ม RPC และ Reads 0

### P3 — วัดคอขวด แล้วลดข้อมูลที่อ่านก่อนเพิ่มการอ่านขนาน

1. **เก็บ baseline ก่อนปรับ** — ใช้เวลาตั้งแต่คลิกเมนูถึงข้อมูลแรกที่ค้นหา เปิดรายละเอียด หรือทำงานได้ วัดแยกเวลาเปิด iframe/เริ่ม UI, รอคิว, ตรวจสิทธิ์, ทำงานของ gateway, Firestore HTTP, แกะข้อมูล และแสดงผล ใช้ตัวจับเวลาแต่ละฝั่งและเทียบด้วยรหัสคำขอที่ไม่เปิดเผย token รายงาน p50/p95 จำนวนตัวอย่าง อัตราสำเร็จ/หมดเวลา คำขอจริง และจำนวนเอกสารแยกจากขนาดผลตอบกลับ วัดเวลาจน Dashboard สรุปครบอีกชุด แยกรอบเปิดครั้งแรก เปิดซ้ำ หลัง Cache หมดอายุ หลังข้อมูลเปลี่ยน และช่วงคิวค้าง [Google SRE: Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)
2. **Dashboard ตอนเปิดครั้งแรก** — เริ่มที่ `dashboardBootstrap_`, `queryDashboardMovementsRange_` และ `buildPoVendorMapForMovements_` วัดว่าช้าเพราะจำนวนรายการเคลื่อนไหว ขนาดข้อมูล หรือการอ่านใบสั่งซื้อย้อนหลัง แยกโหลดรายละเอียดที่ยังไม่เปิดเฉพาะเมื่อพิสูจน์แล้วว่าไม่ใช่ข้อมูลที่ต้องคำนวณยอดบนหน้าแรก คงช่วงวันที่ตามเวลาไทย ความครบของช่วงที่ใช้คำนวณยอด ต้นทุนย้อนหลัง และรายการย้อนผล แยกการโหลดประวัติและการกู้เมื่อส่วนนี้ล้มเหลว การรวมข้อมูลหลายชุดต้องใช้มุมมองข้อมูลที่สอดคล้องกันตาม `readTime` เดิม [Dashboard.gs](../Dashboard.gs) · [Firestore runQuery](https://firebase.google.com/docs/firestore/reference/rest/v1/projects.databases.documents/runQuery)
3. **ตารางและการค้นหา** — ใช้ `where`, `limit`, cursor และ `select` สำหรับตารางปกติและการค้นหาแบบที่ Firestore รองรับ ใช้ลำดับที่คงที่แล้วตรวจหน้าซ้ำ/หายเมื่อข้อมูลเปลี่ยน โหลดรูปและรายละเอียดเมื่อคลิก ใช้ `:batchGet` กับรหัสเอกสารที่ทราบและตัดรหัสซ้ำก่อนเรียก อ่านฟิลด์เท่าที่ต้องใช้ `select` ลดขนาด payload ส่วนการลดเอกสารที่อ่านจึงลด document Reads การค้นหาคำบางส่วนและ XLFilter ต้องเทียบผลกับแค็ตตาล็อกครบชุดก่อนเปลี่ยนวิธี กรณีต้องใช้ดัชนีใหม่หรือบริการค้นหาให้แยกข้อเสนอพร้อมหลักฐาน [StructuredQuery](https://firebase.google.com/docs/firestore/reference/rest/v1/StructuredQuery) · [Firestore query cursors](https://firebase.google.com/docs/firestore/query-data/query-cursors) · [Firestore pricing](https://firebase.google.com/docs/firestore/pricing)
4. **ใช้ `fetchAll()` เฉพาะคำขออิสระที่วัดแล้วว่าคุ้ม** — Master และข้อมูลอ้างอิงสินค้ามีใช้อยู่แล้ว ผู้สมัครที่ชัดคือ `buildPoVendorMapForMovements_` เมื่ออ่านใบสั่งซื้อหลาย batch จริง เปรียบเทียบจำนวน batch เวลา p95 และขนาดตอบกลับก่อน/หลัง จำกัดจำนวนงานที่พร้อมกัน ตรวจว่ารับเอกสารครบหรือแยกกรณี missing ได้ และคงพฤติกรรมเมื่อคำขอย่อยล้มเหลว หน้า `pageToken` ถัดไปและช่วงที่ต้องใช้ `readTime` จากผลก่อนหน้าต้องรักษาลำดับเดิม การส่งพร้อมกันมีเป้าลดเวลารอ จำนวน Reads ของเอกสารชุดเดิมยังเท่าเดิม [Apps Script best practices](https://developers.google.com/apps-script/guides/support/best-practices) · [UrlFetchApp](https://developers.google.com/apps-script/reference/url-fetch/url-fetch-app) · [Firestore batchGet](https://firebase.google.com/docs/firestore/reference/rest/v1/projects.databases.documents/batchGet)
5. **Cache และความถูกต้อง** — คง in-memory, IndexedDB และ Script Cache ตามหลักฐานปัจจุบัน วัด hit/miss, ค่าใช้จ่ายในการตรวจเวอร์ชัน และการอ่านใหม่เมื่อ Cache ใช้ไม่ได้ก่อนปรับ TTL ปัจจุบัน Master ทั่วไป 15 นาทีและสินค้า 5 นาที จำกัดขนาดและตรวจรุ่นของชุดข้อมูลเมื่อ invalidation ห้ามใช้ Cache เป็นข้อมูลตัดสินใจตอนยืนยันตัดสต๊อกหรือแก้บิล รักษาการตรวจสิทธิ์ การตรวจข้อมูลล่าสุด ฝั่งเซิร์ฟเวอร์ และเงื่อนไขธุรกรรมเดิม [ReadCache.gs](../ReadCache.gs) · [CacheService](https://developers.google.com/apps-script/reference/cache/cache) · [Firestore transactions](https://firebase.google.com/docs/firestore/manage-data/transactions)

Query Explain เป็นเครื่องมือวิเคราะห์เฉพาะ query เลือกใช้เมื่อหลักฐานชี้ว่าติดที่การอ่านหรือ index และมีช่องทางที่สอดคล้องกับสิทธิ์โครงการ โหมด analyze รัน query จริงและมีผลต่อค่าใช้จ่ายตามเอกสาร การเพิ่ม indexes หรือข้อมูลสรุปล่วงหน้าควรเป็นงานแยกเมื่อวิธีที่ไม่เปลี่ยน DB ยังไม่ถึงเป้าหมาย [Firestore Query Explain](https://firebase.google.com/docs/firestore/query-explain)

| C · การวัด | เตรียม fixture 10,000 SKU, กรณีประวัติหนาแน่น และแบบเก็บข้อมูลก่อน–หลังได้พร้อมงานแก้บัค | เก็บ baseline แยกจากชุดทดสอบอื่นที่ใช้ทรัพยากรเครื่องเดียวกัน ใช้ไฟล์ผลและพอร์ตแยกสำหรับชุดที่รันพร้อมกัน |
| D · ปรับการอ่าน | สำรวจ query และเตรียมข้อเสนอได้พร้อม C | เริ่มเปลี่ยน query/Cache หลัง baseline ชี้คอขวดและงานแก้บัคชุด A กับ B ผ่าน แยก commit ตามการปรับแต่ละจุดเพื่อวัดผลและย้อนกลับง่าย |

## เกณฑ์ตรวจรับและส่งมอบ

- รัน `npm run check`, `npm test`, `npm run test:browser`, `npm run test:browser-backend` และ `npm run release:prepare` ตรวจทั้งชุด source และไฟล์ที่เตรียมปล่อยให้ตรง commit พร้อมทดสอบ Admin/Staff/Viewer เปิดเมนู ค้นหา XLFilter เปลี่ยนหน้า เปิดรูป/รายละเอียด ใบเสนอราคา ประวัติ แก้บิล และสต๊อกกับข้อมูลจำลอง
- เทียบ workload เดียวกัน เช่น เปิดครั้งแรก/เปิดซ้ำ หน้าถัดไป ค้นรหัส ค้นคำบางส่วน ใช้ XLFilter เปิดรูป สลับหน้าระหว่างคิวค้าง โหลด Dashboard หลังสต๊อกเปลี่ยน และประวัติล้มเหลว รายงานจำนวนตัวอย่าง ความสำเร็จ p50/p95, RPC, Firestore HTTP, ขนาดข้อมูล และ Reads/Writes แยกกัน นับคำขอล้มเหลวในอัตราข้อผิดพลาด เก็บค่าการจำลองแยกจากค่า billed Reads ซึ่งอาจรวม index entries และค่าอ่านขั้นต่ำ [Firestore pricing](https://firebase.google.com/docs/firestore/pricing)
- เป้าหมาย Production คือ **p95 ≤ 10 วินาทีตั้งแต่คลิกจนข้อมูลชุดแรกใช้งานได้ต่อหน้า** และ **Reads หลังปรับ ≤ 10 เท่าของ baseline ต่อภาระงานที่สำเร็จและเทียบกันได้** ตั้งเป้า Reads ปกติเท่าเดิมหรือลดลง แยกช่วง Backup และกรณี retry ออกจากตัวเลขใช้งานปกติ พร้อมรายงานผลรวม หาก baseline เป็นศูนย์ให้รายงานจำนวน Reads ที่เพิ่มและเหตุผลแทนอัตราส่วน กรณีทดสอบในเครื่องยืนยันพฤติกรรมและจุดถดถอย แต่ยังไม่ยืนยัน p95 หรือ billed Reads บน Production
- เมื่อผ่าน ให้ทำ commit และ Push `main` ตาม `AGENTS.md` แยก commit ของบัคร่าง บัค Dashboard และการปรับประสิทธิภาพ รายงานไฟล์ ผลทดสอบ ผลกระทบต่อ Firestore, SHA, สถานะ Deploy และงานค้าง หากได้รับอนุญาตให้ Deploy ให้บันทึกเวอร์ชันจริงและเตรียมทางย้อนรุ่นเดิมเมื่อพบผลถดถอย พร้อมตรวจด้วยการอ่านอย่างเดียวตามข้อจำกัด Production
