# SYY-Shop — งานแก้การโหลดข้อมูล ปรับ Cache และแยก `Code.gs`

เริ่มจาก `main` ชุดที่ตรวจแล้ว `cac438d` แล้วตรวจ `origin/main` และ `AGENTS.md` ก่อนแก้ไข เอกสารนี้ใช้ส่งต่องานเมื่อผู้ใช้สั่งเริ่ม เป้าหมายคือให้เมนูเปิดใช้งานได้เร็ว เก็บร่างผู้ใช้ครบ และคงผลค้นหา XLFilter สิทธิ์ และความถูกต้องของยอดสต๊อกตามเดิม ใช้ Firestore จำลองสำหรับการทดสอบที่มีการเขียน การตรวจระบบจริงใช้การอ่านผ่านระบบเดิมเท่านั้น และ Production Deploy ต้องได้รับอนุญาตสำหรับชุดที่จะปล่อย

## ลำดับงาน

1. **ป้องกันร่างสูญหาย** — `Shared.html` ข้ามร่างที่ `ready` ยังเป็น `false` แต่ฟอร์มใบเสนอราคาเปิดให้พิมพ์ระหว่างรอข้อมูลได้ จัดให้การติดตามร่างพร้อมก่อนรับการพิมพ์ หรือเก็บการแก้ไขช่วงแรกไว้โดยเฉพาะ แล้วรวมกับข้อมูลที่โหลดมาทีหลังโดยรักษาค่าที่ผู้ใช้แก้ ทดสอบกรณีมีร่างเดิม โหลดช้า เซสชันหมดอายุ และกู้ร่างหลังเข้าใหม่ ตรวจฟอร์มใบเสนอราคา ใบกำกับ สั่งซื้อ สินค้า และตัดสต๊อกที่ใช้ตัวเก็บร่างร่วมกัน
2. **กู้คิวคำขอที่ค้าง** — `Shared.html` มี 3 ช่องต่อคิวที่แชร์กัน หน้าจอหมดเวลาหลัง 45 วินาที แต่ช่องยังถูกถือไว้จนได้ผลหรือถึงเวลาทำความสะอาด จึงพบคำขอที่ปกติหมดเวลาทั้งที่ยังไม่ส่ง แยกการวัดเวลารอคิวกับเวลารอเซิร์ฟเวอร์ ทดลองช่องสำรองสูงสุด 1 ช่องสำหรับงานอ่านหน้าที่ผู้ใช้เปิดเมื่อช่องปกติค้างครบ คำขอซ้ำที่ยังไม่คืนผลให้รวมกับคำขอเดิม รักษาการตรวจเวอร์ชันหลังข้อมูลเปลี่ยนและใช้กรอบจำกัดคำขอเดิมฝั่งเซิร์ฟเวอร์ ทดสอบให้จำนวนคำขอจริงมีเพดาน คำตอบเก่าไม่ทับผลใหม่ และคำสั่งเขียนไม่ถูกส่งซ้ำอัตโนมัติ
3. **แยกการใช้งานสินค้าใน Dashboard จากประวัติ** — `index.html` จำกัดตัวอย่างไว้ 50 แถวและปิดค้นหาเมื่อประวัติไม่พร้อม ให้ค้นหาและแบ่งหน้าจากสินค้าที่โหลดมาแล้วโดยไม่เพิ่ม RPC แสดงสถานะของประวัติและยอดที่ยังไม่พร้อม พร้อมลองโหลดเฉพาะส่วนที่ล้มเหลว ทดสอบกรณีมี 120 รายการและประวัติล้มเหลว แล้วค้นหารายการที่ 120 ได้โดย Reads ไม่เพิ่ม ตรวจยอดขาย ต้นทุน และผลจากการแก้บิลเมื่อข้อมูลครบ
4. **แยกเวอร์ชันออกจากการจัดเก็บชุดสินค้า** — `index.html` และ `Shared.html` อาศัยการกู้ Cache เพื่อส่งเวอร์ชันไปยัง `getDashboardBootstrap` จึงรับชุดสินค้าซ้ำเมื่อ IndexedDB ใช้ไม่ได้หรือข้อมูลเกินเพดาน ให้เก็บเวอร์ชันและเวลาไว้คู่กับรายการที่หน้าเว็บถืออยู่ ผูกกับเซสชันและการล้าง Cache ให้ `Code.gs` ตรวจเวอร์ชันกับอายุอีกครั้งก่อนเลือกส่งเฉพาะประวัติ ทดสอบข้อมูล 10,000 รายการที่เกินเพดาน รวมกรณีสต๊อกเปลี่ยนระหว่างสองคำขอ คงการขอชุดใหม่เมื่อเวอร์ชันไม่ตรง
5. **ทดลองตัด Cache เฉพาะชั้น** — เทียบระบบเดิมกับปิดเฉพาะ IndexedDB ผ่านสวิตช์ `SYY_HYBRID_CACHE` ในชุดทดสอบ คง Cache ในหน้าและฝั่ง Apps Script สำหรับ Master, XLFilter และประวัติที่ใช้ซ้ำ ตารางปกติให้ใช้ cursor และ limit พร้อมโหลดรูปหรือรายละเอียดเมื่อคลิก หากผลทดสอบบอกว่า IndexedDB เพิ่มเวลาหรือภาระดูแลโดยช่วย Reads น้อย ให้เสนอปิดเฉพาะชุดข้อมูลนั้น คงการตรวจข้อมูลจริงฝั่งเซิร์ฟเวอร์ก่อนตัดสต๊อกหรือบันทึกบิล

6. **แยก `Code.gs` ตามหน้าที่ หลังชุดแก้การโหลดผ่านการทดสอบ** — ย้ายโค้ดทีละกลุ่มโดยคงพฤติกรรมเดิม เริ่มจาก `Catalog.gs` สำหรับรายการสินค้า ค้นหา และ XLFilter กับ `Dashboard.gs` สำหรับการอ่านข้อมูลและสรุปยอด จากนั้นจึงแยก `ReadCache.gs` สำหรับเวอร์ชันและการใช้ Cache ซ้ำ กับ `Firestore.gs` สำหรับการติดต่อฐานข้อมูล โดยสำรวจการพึ่งพาระหว่างสองส่วนก่อนเลือกย้ายส่วนที่แยกได้ก่อน คง `doGet`, `apiGateway`, ตารางสิทธิ์ จุดเข้าใช้งานเดิม และธุรกรรมสต๊อกไว้ใน `Code.gs` สำหรับชุดนี้ คงชื่อฟังก์ชันที่เบราว์เซอร์หรือ Trigger เรียก ชื่อ API และข้อตกลงของข้อมูลที่รับส่ง ตรวจชื่อในขอบเขตตัวแปรร่วมและหลีกเลี่ยงงานที่รันระดับไฟล์แล้วขึ้นกับลำดับโหลด

## งานที่ทำพร้อมกันได้และจุดรวม

ก่อนเริ่ม ให้บันทึก baseline บน `main` ล่าสุดและระบุผู้รับผิดชอบแต่ละส่วน ตารางนี้ใช้ได้ทั้งกับการทำทีละคนและการแบ่งงานเมื่อมีผู้ทำหลายคน

| ช่วง | ทำพร้อมกันได้ | จุดรวมและงานที่ต้องรอ |
|---|---|---|
| **1. แก้บัคและเตรียมเครื่องมือ** | **A** เก็บร่างในส่วน draft ของ `Shared.html` และฟอร์มที่เกี่ยวข้อง · **B** กู้คิวในส่วน transport ของ `Shared.html` · **C** ทำ Dashboard ข้อ 3–4 ใน `index.html` และเตรียมกรณีประวัติล้มเหลว/ชุดสินค้าใหญ่ · **D** สำรวจรายการไฟล์ในตัวจัดชุด Deploy และชุดทดสอบ พร้อมเตรียม fixture และชุดวัดเปรียบเทียบ | A, B และ C ใช้ `Shared.html` ร่วมกัน ให้แต่ละงานรับผิดชอบคนละฟังก์ชัน กำหนดรูปแบบผลตอบกลับก่อน แล้วให้คนเดียวรวมการแก้ `callApi`, การล้าง Cache และ session expiry หากสองงานต้องแก้ฟังก์ชันเดียวกัน ให้รวมงานนั้นตามลำดับแทนการแก้พร้อมกัน ข้อ 3–4 รวมเป็นชุดเดียวเพราะใช้สถานะสินค้าและเวอร์ชันร่วมกัน งาน D เตรียมเครื่องมือได้ทันที การแก้ test harness ที่ไฟล์เดียวกับ A–C ให้ประสานก่อนรวม |
| **2. ตรวจผลรวมและเทียบ Cache** | หลังรวม A–C ให้รันทดสอบหน้าจอ สิทธิ์ และ backend พร้อมกันได้เมื่อแยกพอร์ตและแฟ้มผลทดสอบ | วัดเวลาเปิด/ปิด IndexedDB ทีละแบบบนเครื่องเดียวกันโดยกันภาระจากชุดทดสอบอื่น หรือใช้เครื่องวัดแยก ใช้ source และข้อมูลชุดเดียวกัน เปรียบเทียบเวลา Reads และความถูกต้องก่อนตัดสินใจว่าจะปิดส่วนใด เก็บ commit ชุดแก้พฤติกรรมแยกจากชุดย้ายไฟล์ |
| **3. แยกบริการ Catalog และ Dashboard** | เตรียมแผนย้ายและตรวจการพึ่งพาของสองบริการพร้อมกันได้ ตัวจัดชุด Deploy และชุดทดสอบต้องรองรับการโหลดไฟล์ใหม่ก่อนเริ่มย้าย | ให้ผู้รับผิดชอบคนเดียวรวมการแก้ `Code.gs` ย้ายและทดสอบ Catalog ก่อน แล้วจึงย้าย Dashboard จากฐานใหม่ โดยเฉพาะส่วนที่ Dashboard เรียกชุดข้อมูล Catalog ทดสอบว่าชุด Deploy มีไฟล์ที่ย้ายครบก่อนรวมแต่ละ commit |
| **4. แยก Firestore และ Read Cache** | ทำแผนที่ผู้เรียก ตรวจขอบเขตส่วนอ่าน และตรวจผลต่อธุรกรรมพร้อมกันได้ | เริ่มหลังช่วง 3 ผ่าน ย้ายส่วนที่แยกได้ทีละชุดและตรวจ cold/warm, invalidation, สิทธิ์ และสต๊อกหลังแต่ละชุด หากยังพึ่งตัวแปรร่วมกับธุรกรรม ให้เก็บส่วนที่เกี่ยวข้องไว้ใน `Code.gs` แล้วบันทึกขอบเขตที่เหลือ |

ก่อนย้ายไฟล์ ให้ตรวจ `scripts/prepare-release.cjs`, `tests/support/services.cjs`, `tests/backend.test.cjs`, `tests/security.test.cjs` และ `tests/release.test.cjs` รวมถึงจุดอื่นที่อ้าง `Code.gs` โดยตรง ให้ชุดทดสอบและชุด Deploy เห็นไฟล์ `.gs` ที่ใช้จริงครบตามลำดับที่กำหนด คงการตรวจ route map และการแปลง Project ID กับเส้นทางอีเมลของชุด Staging ให้ผ่านการทดสอบเดิม เอกสารข้อจำกัดเรื่องขอบเขตตัวแปรร่วมและลำดับโหลดอยู่ที่ [Apps Script V8](https://developers.google.com/apps-script/guides/v8-runtime#module_limitations)

เมื่อรวมงาน ให้ใช้ `main` ตาม `AGENTS.md` แยก commit ของการแก้พฤติกรรม งานเตรียมชุด Deploy และการย้ายไฟล์ เพื่อให้ตรวจผลและย้อนเฉพาะชุดได้

## เกณฑ์ตรวจรับและส่งมอบ

- รัน `npm run check`, `npm test`, `npm run test:browser` และ `npm run test:browser-backend` พร้อมเพิ่มกรณีถดถอยตามข้อ 1–4 ตรวจ Admin, Staff และ Viewer การค้นหา XLFilter เปลี่ยนหน้า เปิดรายละเอียด และกู้ร่าง
- เทียบภาระงานชุดเดียวกันบนข้อมูลจำลอง 10,000 สินค้า เช่น เปิดครั้งแรก เปิดซ้ำ เปิดหลังข้อมูลเปลี่ยน ค้นหา กรอง เปลี่ยนหน้า และคิวค้าง รายงานข้อมูลที่ส่ง เวลา และจำนวนคำขอจริงแยกจาก Firestore Reads และ Writes แยกผลปกติออกจากผลจำลองการกู้คิว
- เมื่อมีการอนุมัติปล่อย ให้เทียบระบบจริงด้วยข้อมูลอ่านอย่างเดียว วัดจากคลิกเมนูจนข้อมูลชุดแรกใช้งานได้เป็น p50/p95 รายหน้า แยกเปิดครั้งแรกกับเปิดซ้ำ และวัดเวลาจนยอด Dashboard ครบต่างหาก เป้าหมาย p95 ไม่เกิน 10 วินาทีและ Reads ต่อภาระงานเทียบเคียงไม่เกิน 10 เท่าของ baseline ผลจำลองใช้ยืนยันพฤติกรรมของโค้ด ส่วนผลจากระบบจริงใช้ยืนยันเป้าหมายเวลาและ Reads
- หลังการย้ายไฟล์แต่ละชุด ให้สร้างชุดปล่อยด้วย `npm run release:prepare` และตรวจว่า manifest, ไฟล์ที่เพิ่ม, หน้าและ API เดิม, สิทธิ์ และการแยก Staging ถูกต้อง รายงานผลทดสอบจากชุดปล่อยเดียวกับ source ที่จะนำไปใช้งาน การย้ายไฟล์ควรให้เวลาและ Reads ใกล้เคียงชุดก่อนย้าย
- สรุปไฟล์ที่แก้ ผลทดสอบ Reads/Writes เทียบเดิม ข้อจำกัดที่ยังพบ SHA บน `main` และสถานะ Deploy ผลตรวจเบื้องต้นอยู่ใน `test-results/REAUDIT-SUMMARY-2026-11-15.md` หากเปิดจาก checkout อื่น ให้ใช้กรณีทดสอบสี่ข้อในเอกสารนี้และอ่านแนวทางเดิมจาก [รายงานการแก้การโหลด](LOADING-RELIABILITY-2026-11-15.md)
