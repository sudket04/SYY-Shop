## 3. ผลกระทบต่อ Modules และ Data Integrity

Auth workers ยังมี targeted security reads ที่จำเป็นต่อ durable revocation;ไม่ได้ใช้ cached profile แทน credentials/counters. Throttle ใช้ Script Properties เป็น operational metadata ไม่มี collection ใหม่ ไม่มี raw username/email/token ใน property keys. Hash buckets อาจชนกัน จึงต้องทดสอบกับปริมาณ login จริงใน staging.

Master forms จับ baseline version ตอนเปิดฟอร์ม จึงไม่เปลี่ยน baseline เงียบ ๆ หาก background refresh มาระหว่างแก้ไข. Writes preserve unknown fields. Product stock baseline และ atomic Stock Issue/Receive Goods/replay/quote marker จากข้อ 1–18 ยังผ่าน regression. Reference lock reuse ป้องกัน nested auto-ID lock; external Firestore/admin writers ที่ไม่ผ่านแอปต้องมี coordination ของตนเอง.

การลบมีข้อจำกัดเพิ่มโดยตั้งใจ: Master ที่ถูกอ้างอิง, Product ที่มี stock/transaction/document history, PO ที่รับสินค้าแล้วหรือมี receipt/movement history ลบไม่ได้. Historical Invoice customer/items เป็น snapshot เดิม ไม่ย้อนแก้. ไม่เพิ่ม soft-delete/archival schema หรือ backfill. Car fields ใช้ collection/form เดิมและรักษาค่า legacy.

Invoice/Quote/PO paging ไม่มี silent cap. Cursor ผูก collection/project/year, จำกัดขนาด, ตรวจรูปแบบและอายุ <55 นาที; next page ใช้ readTime เดิม. Cursor หมดอายุ/error คงรายการเดิมและเสนอ retry/refresh. การกด Load All เป็นการอ่านครบตามคำขอผู้ใช้ ไม่ใช่การอ่านฟรี และต้องรอครบก่อนสรุปทั้งปี. Pending PO codes/count อ่านเฉพาะ open statuses ใน query เดียวพร้อม projection และ readTime ของหน้า PO เพื่อไม่ให้ first-page history ทำสัญญาณคำสั่งซื้อค้างผิด.

Dashboard เปลี่ยนความหมายของข้อมูลให้ชัดเจน: default โหลดปีปัจจุบันและปีก่อน, historical year โหลด on demand พร้อม current health window. ไม่เรียกการขาด activity ใน window ว่า “ไม่เคยเคลื่อนไหว”. การเลือกปีเก่ามากอาจต้องอ่านสองช่วง report/health. ยังคง reconciliation ประมาณ 5 นาทีเมื่อ Dashboard active เพื่อความถูกต้อง.

## 5. Security และขอบเขตการเปลี่ยนแปลง

Public browser-callable surface ยังคง 8 endpoints, operation names/roles V1/V2 เดิม. Staff/Viewer ไม่ได้สิทธิ์ตั้ง TOTP เพิ่ม. Reference read/query errors fail closed. Reset/forced tokens ถูกผูกกับ durable credentials/version และไม่ consume ก่อน validation/write ยืนยันสำเร็จ.

## 6. UX และ Error Recovery

Draft customer/basket/negotiated prices ไม่ถูกรีเซ็ตเมื่อข้อมูลใหม่เข้ามา; stock/name/reference lists reconcile ตามขอบเขต. Stale year reply ไม่เปลี่ยนหน้าที่เลือก. Successful write ไม่ถูกแสดงให้ผู้ใช้ retry เพียงเพราะ subsequent list/cache refresh ล้มเหลว. Product failed refresh ปลด busy และอัปเดต count ทั้งสองตำแหน่ง.

Modal รองรับ keyboard loop, return focus, screen-reader semantics และ inert background แม้ overlay อยู่ภายใน page-body; SYY searchable selects และ SweetAlert focus ยังใช้ได้. Escape/backdrop ไม่ถูกเพิ่มเป็น close action ตาม policy เดิม. PO card/table tested at 320/390 px; table ยังเลื่อนได้ภายใน container.

Browser artifacts อยู่ใน ignored `test-results/` เช่น `po-mobile-320.png`, `po-mobile-390.png`, `quotation-desktop.png`, `quotation-mobile-quick-add.png`, `browser-result.json`; เป็น fixture data และไม่ได้ publish.

## 8. Firestore Read/Write Impact และผลจำลอง

**ยังไม่มีเปอร์เซ็นต์ลดทั้งระบบที่วัดจาก Production.** ตัวเลขต่อไปนี้เป็นสถานการณ์จำลองเฉพาะเส้นทาง และนับ query document results ไม่ใช่ billed reads รวม:

| Scenario | ก่อน → หลัง | ผลจำลอง |
|---|---|---|
| Dashboard, 1,000 movements ต่อปี ×5 ปี | 5,000 → 2,000 default | **ลด 60%** ของ movement docs ใน fixture; response 518,398 bytes |
| Invoice ปีที่มี 1,207 ใบ เทียบ old year cap 1,000 | initial 1,000 → 51 (50 + lookahead) | **ลด 94.9%** ตอนเปิด; UI ระบุยังไม่ครบ |
| Invoice Load All ใน fixture เดียวกัน | complete 1,207 → 1,213 document results | อ่านเพิ่ม 6 lookahead docs (~0.50%); ได้ครบแทน old truncated list |
| Cleanup logs 10,000 โดยหมดอายุ 300 | 10,000 → 300 | **ลด 97%** ของ query docs; delete คง 300, HTTP commit 1 ครั้ง |
| Product bootstrap 500 records | 2 → 1 GAS RPC | **ลด round trips 50%**; payload 229,428 bytes (masters 233 bytes) ไม่ใช่ Firestore reduction 50% |

กลไกอื่น: same-year document saves ไม่ reread list/years; PO mutation ใช้ returned DTO/targeted conflict read; normalized account lookup ไม่อ่านทุก User สำหรับ identity ปกติ; cold product readback อ่านเฉพาะ reference docs. Cache generation/fresh security/version/reference checks เพิ่ม reads/Script Property calls ที่จำเป็น. Delete/reference checks บางเส้นทางยังต้องอ่าน history ครบเพื่อไม่ให้ลบข้อมูลที่ถูกอ้างอิง.

**ข้อจำกัดที่รักษาไว้เพื่อ correctness:** เมื่อ monthly running counter ยังไม่มี ต้อง seed จากเลขเดิมครบ collection เพราะวันที่อาจถูกแก้โดยคงเลขเดิม; projection ลด payload แต่ไม่ลด document-read billing. ไม่ fallback สแกนซ้ำเมื่อ counter/service ผิดพลาด. Legacy mixed-case users อาจต้อง initial ID-index scan; open PO summary อ่าน open orders ทั้งหมด. Dashboard ยัง aggregate raw rows ใน bounded windows; การเพิ่ม summary collections/index/backfill ต้องออกแบบและได้รับอนุมัติแยก.

Batch delete ลด HTTP overhead ไม่ได้ลดจำนวน billed deletes. Projection ลด bytes ไม่ใช่ read charge; cursor queries มี `__name__` และอาจมี index-entry reads ต้องวัดด้วย Query Explain/metrics จริง. ห้ามนำเปอร์เซ็นต์ในแต่ละ fixture มาเฉลี่ยเป็นเปอร์เซ็นต์ประหยัดทั้งระบบ.

## 10. งาน rollout ที่ยังต้องยืนยันและหลักฐานอ้างอิง

ก่อนอนุมัติ rollout: staging UAT ด้วยขนาดข้อมูลจริงและหลาย sessions, expired/snapshot cursors และ name/date indexes, first-admin/reset/forced flows/Mail delivery, role matrix, Properties quota/hash-bucket contention, reference-lock latency, nested HtmlService frame lifecycle, mobile/keyboard/PDF/export และ read/write/index-entry metrics. Snapshot cursor ไม่ใช่ข้อมูล live ตลอดเวลา; Refresh เพื่อรับ mutations ของ session อื่น.

Cache generation อยู่ใน durable Properties; unique chunks ป้องกัน mixed snapshots. หาก property write หลัง business commit ล้มเหลว จะ invalidate manifest/bypass ด้วย cache marker เท่าที่ CacheService ยังพร้อม และไม่ทำให้ผู้ใช้เขียนซ้ำ. การล้มเหลวพร้อมกันหรือ eviction ระหว่าง property outage ไม่ใช่ distributed consistency guarantee; ต้องติดตาม service quota/errors ใน staging. External writers ต้อง coordinate invalidation/reference changes.

Rollback ใช้ reviewed Source baseline โดยคงข้อมูลใหม่ที่ถูกต้อง; ห้ามคืน snapshot Production หรือ reverse user permissions โดยอัตโนมัติ. ต้องจัดการ cache v2/v3 ระหว่าง rollout/rollback ภายใต้การอนุมัติ เพราะ Source รุ่นเก่าไม่อ่าน generation ใหม่. Deploy client/backend พร้อมกันเพื่อให้ pagination/combined-bootstrap response ตรงกัน. ไม่ดำเนินขั้นตอนเหล่านี้ในงาน local นี้.
